# 025 - 메모리 줄이기 1차 (측정 · 아레나 · 문자열 공유)

## 왜

Koyeb 메모리 그래프가 512MB 중 500MB 근처인데, 그 숫자에 커널 파일 캐시가 섞여 있어 실제 사용량을 몰랐다. 023 에서 넣은 표 캐시가 39MB 를 쓰고 있어 줄일 수 있는 것부터 손봤다.

## 문제

- 로컬 측정: 앱 import 만 153MB. `google.cloud.bigquery` 하나가 114MB 이고 pandas·numpy·pyarrow·grpc 를 함께 끌고 온다. 그래서 우리 코드의 pandas 를 걷어내도 절감이 0 이다.
- 표 캐시 상주 39MB 중 상당 부분이 같은 문자열의 중복이다 (포인트 42,840행의 user_id·reason·category).

## 해결

- `utils.process_rss_mb()`: `/proc/self/status` 의 VmRSS 를 읽고, 없으면 rusage 로 폴백. 부팅 로그와 10분마다 도는 BigQuery 업로드 로그에 한 줄씩 남긴다.
- Dockerfile `MALLOC_ARENA_MAX=2`: glibc 가 스레드마다 아레나를 잡아 RSS 를 부풀리는 것을 막는다.
- `table_cache.INTERNED_COLUMNS`: 값이 반복되는 열(user_id·category·type·reason 등)만 `sys.intern` 으로 모은다. id·url·본문처럼 값이 거의 다 다른 열은 넣지 않는다 (모아 둘수록 손해).
- TDD 신규 3 (VmRSS 파싱 · 폴백 · 반복 열 공유). 전체 423 passed.

## 결과

- 표 캐시 상주 39.4MB → **26.4MB**, 읽는 순간 최대 44.1MB → 31.1MB. 워밍업 시간은 88ms 로 그대로.
- 메모리 로그와 아레나 제한의 효과는 배포 로그로 확인한다.
- 다음 후보(사용자 결정 대기): BigQuery 적재를 가벼운 REST 로(단독 약 34MB) + 우리 코드 pandas 제거(단독 0MB). 둘을 같이 해야 약 95MB 다.

## 사용자 검증 방법

1. 배포 로그에 `표 캐시 워밍업 완료: N초 · 메모리 NNN MB` 가 찍힌다. 이 숫자가 실제 프로세스 메모리다.
2. 10분 뒤 `BigQuery 업로드 작업 완료 · 메모리 NNN MB` 로 시간에 따른 변화를 본다.
3. Koyeb 그래프와 비교한다. 그래프가 500MB 인데 로그가 300MB 대면 나머지는 커널 파일 캐시다.
4. 기능은 그대로여야 한다. 홈 탭 · 포인트 내역 · 게시판.
